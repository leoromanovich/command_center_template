# Control Center agent protocol

Этот репозиторий — карта и исполняемый control plane для sibling-проектов.

## Bootstrap trigger

Если пользователь просит создать, настроить или мигрировать CC:

1. прочитай `BOOTSTRAP.md`;
2. загрузи skill `grill-cc-bootstrap`;
3. определи режим `new` или `migration`;
4. веди grilling до проверяемого состояния, а не до получения первого ответа.

Не изобретай для CC новую топологию: базовые clones живут в `source_repos/`, feature worktrees — в `wt/<feature>/<repo>_wt/` внутри корня CC; обе папки gitignored. Состав репозиториев CC определяют grilling-инвентаризация bootstrap и `./cc repo scan`.

Если пользователь просит спланировать сложную или агентную задачу, загрузи `grill-task-planning`. Храни текущие планы в `plans/active/`, отменённые — в `plans/archived/`, выполненные — в `plans/completed/`; переходы делай через `./cc plan`.

После реализации принятого плана и прохождения acceptance checks загрузи `consolidate-task-knowledge`. Проведи evidence-backed reflection до `./cc plan complete`; не продвигай гипотезы модели в канонические знания. Тот же skill по явному запросу проводит environment retro тяжёлой сессии — propose-only кандидаты улучшения среды агента, без привязки к плану.

## Начало работы

1. Прочитай `docs/index.md`.
2. Открой только относящиеся к задаче заметки и их прямые связи.
3. Выполни `./cc show`, чтобы увидеть реальный исполняемый интерфейс.
4. Перед изменениями определи затронутые projects, workflows и checks.
5. Для каждого затронутого проекта прочитай его `docs/projects/<repo>/index.md` и прямые связи, если index существует.

Не сканируй всю `docs/` и архивы без необходимости.

## Источники истины

- Сборка, тесты, упаковка, запуск и деплой: Nix expressions.
- Runtime-состояние: CI/CD, observability и API целевой системы.
- Причины, ограничения, хаки, решения и техдолг: атомарные Markdown-заметки.
- Код проекта: соответствующий sibling-репозиторий.
- Секреты: внешний secret manager; не этот репозиторий.

## Жёсткие правила

- Не записывай исполняемый процесс пошаговой Markdown-инструкцией.
- Не исправляй drift обновлением описания: исправь Nix-контракт или проект.
- Не обходи Nix прямыми `cmake`, `make`, `docker build` или test-командами, кроме диагностики; найденную рабочую команду перенеси в derivation/check/app.
- Пинь удалённые исходники через flake inputs. Для локальной разработки используй input override, не абсолютные пути в Git.
- Создавай feature worktrees через `./cc worktree`; собирай и проверяй их через `./cc feature <feature> ...`.
- Чистые воспроизводимые действия размещай в `packages`/`checks`; сетевые, интерактивные и привилегированные — в явно запускаемых `apps`.
- Production-действия по умолчанию запрещены и требуют отдельного адаптера, проверки и подтверждения.
- Не сохраняй секреты, полные диалоги и внутренние рассуждения агента.

## Правила знаний

- Одна заметка — один устойчивый факт, решение, хак или долг.
- Каждая заметка имеет frontmatter: `id`, `title`, `status`, `summary`, `verified_at`, `evidence`, `relations`.
- Связи и evidence указываются путями от корня репозитория.
- Объясняй «почему» и границы применимости; не дублируй код.
- Заменённое знание помечай `superseded` и связывай с преемником.
- Хак связывай с решением или техдолгом и условием удаления.
- Завершённая задача имеет reviewed reflection и явный knowledge delta; `none` допустим.
- Daydreaming-кандидаты храни только в ignored `.control-center-knowledge/candidates/` до независимой проверки.

Подробности: `docs/rules/knowledge-layout.md` и `docs/rules/knowledge-consolidation.md`.

## Проверка

Нормальное завершение изменения:

```bash
./cc check
```

Если Nix недоступен, запусти `python3 scripts/validate-knowledge.py .` и явно сообщи, что Nix-часть не проверена.
