# Command Center

Пиши кратко, по-русски. Уточняй требования в чате перед подготовкой плана.

## Процесс

1. Planner читает `docs/repositories.md`, согласует критерии, карту влияния, базовые и feature-ветки, необходимость публикации и Jira.
   Состав рабочих репозиториев определяется только текущим профилем. Пустой `repositories` означает, что сначала нужна настройка; исходники из `examples/` автоматически не подключаются.
2. Каждая новая задача получает уникальный id. План и task.json создаются в draftsRoot текущего профиля. `cc_prepare` автоматически создаёт worktree для выбранных репозиториев.
3. Пользователь проверяет план и одобряет его в `/tasks`. До одобрения реализация запрещена.
4. Контроллер запускает Builder → formatter → format-check/lint/tests → Reviewer. Ошибки возвращаются Builder. Работа завершается проверенным diff для пользователя.
5. Приёмка кода, публикация и обновление базы знаний — отдельные действия пользователя. Никогда не выдавай ответ инструмента за согласие пользователя.

## Границы

- Worktree: `wt/<task>/<repo>`. Основные checkout репозиториев сохраняются.
- Builder исполняет код в Docker через `cc_exec`; `/workspace/<repo>` содержит его worktree. `/context` содержит утверждённые файлы CC. Сеть контейнера отключена; зависимости готовятся в образе.
- Explorer и Reviewer только читают. Git-записи выполняет контроллер по согласованной политике.
- Обязательные проверки находятся в CC; их изменение требует отдельного согласования плана. Проверки конкретной задачи заморожены при prepare.
- Если требуется недоступная операция, Builder формирует конкретный `request_user_action` с целью, командой и cwd, затем останавливается. Пользователь видит выполнение на хосте.
- Если подключён сабмодуль базы: во время реализации он RO. `kb_propose` предлагает необязательные изменения с доказательствами и точными путями. После приёмки пользователь выбирает предложения; тот же Builder обновляет только одобренные страницы.
- Рабочие секреты, `.env` и SSH-ключи должны находиться вне смонтированных worktree.

## Разработка самого пайплайна

Исходники: `runtime/pi`, `runtime/core`, `scripts`. Для правок здесь нужен отдельный запрос пользователя на пайплайн. Не редактируй runtime, профиль или проверки ради прохождения текущей feature-задачи.
Проверки: `npm test`, `npm run test:core`; при изменениях Docker или прав доступа — `npm run test:docker`. Модельные сценарии тестов локальные, без API-вызовов.
